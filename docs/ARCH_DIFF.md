## 0. 一句话结论

例程是**「盲扫物理扇区找 `BM` → 24bit 直通、1 像素占 1 个 32bit 字 → 只留 2 块乒乓 → 整帧突发读经 512 深 FIFO 直通 HDMI；音频另开一颗 PLL 造方波 I2S，再自己收回来」**。

我的实现是**「FAT32 目录索引 → 8 槽帧仓 + 原子提交 → 压缩打包存储（4 像素 3 字）→ 双读端口混合器（特效/缩略图）→ HDMI；音频在像素同时钟域直接合成 24bit PCM，无 I2S、无音频 PLL」**。

四条主线全部不同：**存储发现方式、像素存储格式、缓存结构、音频产生方式**。

## 1. 例程架构的事实基线（可核查）

### 1.1 顶层与时钟

证据：`lab_ex5_i2s/.../top_tf_hdmi_audio.v`

| 项 | 例程做法 | 出处 |
|---|---|---|
| PLL 数量 | **3 个** | L117 / L125 / L133 |
| PLL 分配 | `sys_pll`→100M(SD)/125M(SDRAM)/125M@180°；`video_pll`→25M(像素)/125M(DDR 串行时钟)；`PLL_HDMI_AUDIO`→12.288M | L117-140 |
| 复位 | `rst_all = ~rst_n \| ~audio_pll_lock`（**音频 PLL 没锁就整机复位**） | L114 |
| 可靠性回退 | ex5 的 `sys_pll`/`video_pll` 的 `extlock` **根本没接**；ex4 版本有 20 ms POR 计数器，ex5 删掉了 | L117-130 |
| 时钟域数 | 6：clk / sd_card_clk / ext_mem_clk / video_clk / hdmi_5x_clk / audio_mclk | — |

> ⚠️ **`lab_ex4_tf` 的顶层完全没有音频**：`I_audio_valid/left/right/acr_*` 全部接 0（`lab_ex4_tf/.../top_tf_hdmi_audio.v:351-356`）。
> 文件名里的 "audio" 是遗留。**音频链只有 lab_ex5_i2s 有**，下面 §1.5 讲的是 ex5。

### 1.2 图片发现与解码（红线之一）

证据：`SD/bmp_read.v:69-80,106-137`、`SD/sd_card_bmp.v:205-216`、`top_tf_hdmi_audio.v:160-163`

```verilog
assign header_match = (header_0 == "B") && (header_1 == "M") &&
                      (width[15:0] == bmp_width) && (height[15:0] == bmp_height) &&
                      (bit_count == 16'd24) && (compression == 32'd0);
assign next_scan_sector_if_match = scan_sector + file_sector_count;
assign next_scan_sector_if_miss  = scan_sector + 32'd1;
```

- 从 LBA 0 起**逐扇区**扫描：`SCAN_START_SECTOR=0`、`SCAN_MAX_SECTOR=131071`（=64 MB 上限）、`SCAN_TARGET_COUNT=4`
- 尺寸来自顶层写死常量：`.bmp_width(16'd640), .bmp_height(16'd480)`（L162-163）
- **不读 BPB / 不读 FAT / 不读目录项**：不知道文件长度是否可信、不知道是否碎片化
- 命中后靠 `ceil(file_len/512)` 跳过整张图
- 头里**不检查 `height` 符号**（自顶向下 BMP 会失配）、不校验 `pixel_offset`、行 4 字节对齐靠 640×3=1920 恰好整除这个巧合
- 后果（官方自己的补丁逻辑暴露了问题）：配套脚本 `doc/convert/sync_to_sd.py` 必须**先把卡上旧 BMP 的 'BM' 改成 'XX'** 再拷新图，否则删除残留会被误认

**扫描速度**：每个候选扇区都要完整读 512 B 且**每扇区一次 CMD17**。25 MHz SPI 下每扇区 ≈170 µs，最坏 131072 扇区 ≈ **20 s 以上**——而判定只需要前 54 字节。

### 1.3 像素存储格式（红线之一，v1 漏掉的一条）

证据：`SD/sd_card_bmp.v:82`、`top_tf_hdmi_audio.v:220`

```verilog
// sd_card_bmp.v:82
write_data = {bmp_data[23:16], bmp_data[15:8], bmp_data[7:0], 8'b0};
// top:220  读侧
.read_data (video_read_data[31:8])
```

**24 bit 直通，1 像素占 1 个完整 32 bit 字，低 8 位恒 0 丢弃**。SDRAM 容量与带宽各浪费 25%，帧仓只有 6 槽的余量被白白吃掉 2 槽。

行序倒序**不靠软件翻转**，靠写侧地址映射：`frame_fifo_write.v:46-51,145-159` 用 `VFLIP_FIRST_ADDR_OFFSET=(480-1)*640`、`VFLIP_LINE_JUMP=2*640-1`，每行末地址回跳 1279，把输入第 r 行落到内存第 `479-r` 行。

### 1.4 帧缓存与仲裁（红线之一）

证据：`SD/frame_read_write.v`、`frame_fifo_write.v:82,86`、`frame_fifo_read.v:80,224`、`top:31-33,246-272`

- 地址：`BUF0_ADDR = 0`、`BUF1_ADDR = 307200`；**只接 2 个槽**，`read_addr_2/3`、`write_addr_2/3` 全接 `24'd0`
- **经典双缓冲乒乓**：`write_buf_idx` / `disp_buf_idx`，切缓冲只在帧边界（`disp_buf_idx` 在每帧 `read_req` 的 S_ACK 锁存）→ 这一点例程做对了，不撕裂
- **仲裁是"读写互锁"而不是优先仲裁器**：写侧条件含 `~App_rd_busy`，读侧条件含 `~App_wr_busy`，同一时刻最多一个在突发，靠互相等待交替。**没有优先级，显示侧没有带宽保障**
- 读突发长度依赖**固定的 10 拍 SDRAM 读延迟**（`rd_delay == 4'd10`），且"突发完成"按发出的读命令数计而非实际返回数据数
- **读侧无 underrun 保护**：`read_en` 只按 `de_d[18]` 走，FIFO 空时静默停读，画面表现为像素重复/撕扯，**没有任何空标志检查或错误上报**
- 写侧同样忽略写 FIFO 的 `full_flag`
- **只有 2 块且无预取**：切图要等约 0.3 s 载入 → 做不到瞬时切换，更没有任何特效的硬件基础
- AXIS 无背压：顶层声明了 `O_axis_s_ready` 却从不使用

> 关键结论：**内存里同时只有 2 张图**。而"两帧同时可读"是淡入淡出/滑动的硬件前提——例程的乒乓结构**从结构上做不到**。

### 1.5 音频（红线之一）

证据：`top_tf_hdmi_audio.v:114,133-140,291-323,348-393`；`hdmi_audio_tone_i2s_64fs.v:57-93`；`I2S_receiver.v:42-124`；`audio_arc_calculate.v:4-67`

```
PLL_HDMI_AUDIO(clk2 = 12.288M，clk0/clk1 悬空)
   └─> hdmi_audio_tone_i2s_64fs
          DDS 相位累加器 32bit，只取 bit31 定符号 → 方波（不是正弦，模块名/文档误导）
          AMP = ±2,000,000（−12.5 dBFS）；8 音符 do-re-mi… 每音 0.5 s 循环
          自造"64 bit 声道槽"时序：BCLK=6.144M(=128fs)、每声道 64 BCLK、
          数据左对齐 24bit + 40 个 0、LRCK 低=左、DOUT 在 BCLK 下降沿更新
          └─> I2S_receiver   ← 把刚造出来的 I2S 又解回来（片内自环，不碰引脚）
                 I_rst 端口声明了但**全文未使用**，7 个 always 块全无复位
                 └─> 24bit L/R + audio_valid（video_clk 域）
                        └─> audio_arc_calculate
                               N = 6144 固定；CTS = 用 video_clk 数 48 个样本(1ms)周期数
                               实时测出来 ≈ 25000（±40 ppm 量化误差）
                               └─> HDMI core 的 I_audio_* / I_acr_*
```

三条可被判定为"和例程相同"的指纹：

1. **专门为音频开一颗 PLL** 凑 12.288 MHz（还只用了 clk2）
2. **先生成 I2S 三线再解回来**——而加密 core 的音频接口本来就是**并行 PCM**（`I_audio_valid` / `I_audio_left_data[23:0]` / `I_audio_right_data[23:0]` / `I_acr_valid` / `I_acr_cts[19:0]` / `I_acr_n[19:0]`，见 L378-383）。**这一整圈纯属自找的中间环节，可以直接喂 PCM。**
3. **跨域只靠 I2S 三线上的三拍同步器**，不建音频时钟域、不建异步 FIFO，SDC 里一刀切成 asynchronous

> **更正工作区 `AGENTS.md` 坑 #5**：原文说「I2S 是输入方向，音频从 HDMI 接收侧进 FPGA」。
> 在例程**生效的设计里不成立**——没有 `I_i2s_*` 端口、没有 HDMI 接收核，`pin.adc:8-10` 那三行是 `#` 注释，
> 生效的音频相关约束是 **0 条**。那个说法来自厂商 APUG092 参考设计（那里音频确实从外部 I2S 座子进 FPGA）。

### 1.6 交互

- `key1` → 下一张；`key2` → 自动轮播开/关（L159-160）
- 轮播周期在 `sd_card_bmp` 内由 `CLK_FREQ_HZ` 参数决定，`auto_cnt == CLK_FREQ_HZ-1` → **固定 1.000 s + 单帧加载时间**，**运行期不可配**
- 8 位数码管只显示 `state_code`（4-bit：1 空闲/2 扫描/3 等应答/4 写数据），其余 6 位常量全灭
- 上电只扫一次（`scan_kicked`），**换卡/热插拔必须复位**
- 超时保护：`load_busy` 超过 1.0 s 强制清 busy

## 2. 红线段判读

官方原文：*"提交作品中的整体实现架构、音频和图片处理方法不能和参考实例相同"*。

拆成三个可判定的子句：

| 子句 | 判"相同"的判据 | 我的对策 |
|---|---|---|
| **整体实现架构** | 同一套模块划分（SD→frame_read_write→SDRAM→video_delay→AXIS）、同样双缓冲乒乓、同样 3 PLL 布局、同样读写互锁仲裁 | 重新划分层次；8 槽帧仓 + 显示优先仲裁；只留 2 个 PLL |
| **图片处理方法** | 盲扫扇区找 `BM`；尺寸写死；无文件系统；**24bit 直通、1 像素 1 字、低 8 位丢弃** | FAT32 目录枚举 + 簇链读取；BMP 头全字段校验；**压缩打包存储（4 像素 3 字）** |
| **音频处理方法** | 独立音频 PLL + 内部 I2S 自环 + 方波 DDS 测试音 + 实测 CTS | 无音频 PLL；与像素同时钟域直接合成 24bit PCM；多声部波表；**静态算出 CTS** |

**"复用什么不算照搬"**：SDRAM 控制器（`sdr_as_ram` + 3 个 `.enc.v`）和 HDMI 发送核（`hdmi_1_4b_transmitter_core_wrapper.enc.v`）是**二进制黑盒**，官方只给包装层，任何人都只能用它们——不构成"架构相同"。SD 卡 SPI 协议层属于器件驱动，同理。**判分看的是它们上面那一层怎么组织。**

## 3. 我的架构

### 3.1 存储层：FAT32 目录索引 + 流式 BMP 解码

```
sd_block_reader        扇区级读（复用 SD SPI 协议驱动；阶段三换 CMD18 连续读）
      ↓
fat32_mounter          读 0 号扇区 BPB：bytes/sector、sectors/cluster、reserved、
                       num_FATs、root_cluster、FAT 大小 → 全字段校验，不合法就降级
      ↓
dir_enumerator         根目录簇链遍历，挑出 *.BMP 目录项，把
                       {起始簇, 文件字节数} 写进片上目录表（ERAM，16 项）
      ↓
cluster_walker         按 FAT 表跟随簇链，支持碎片化文件
      ↓
bmp_stream_decoder     校验 'BM' / bfOffBits / biSize / biWidth / biHeight(带符号) /
                       biBitCount(24/32) / biCompression(0)，流式吐像素 + 行号
      ↓
frame_store            写入帧仓槽
```

**与例程的差别**：

- 例程"猜"图在哪（扫魔数）；我"问"文件系统图在哪。伪造命中（图片数据里恰好出现 `BM`，或删除残留）在例程里是真实风险，在我这里不存在。
- 图**数量不设上限**，也不要求文件连续——赛题要求至少 4 张，我给的是"有多少张放多少张（上限 8 张常驻）"。
- 例程 `bmp_width/bmp_height` 是顶层常量；我由 BMP 头决定，**24bit 与 32bit、正反向行序（`biHeight` 符号）都收**，不符规格的图给出诊断码而不是静默花屏。
- **降级路径**：FAT 挂载失败（卡没格式化 / exFAT）→ 自动回退盲扫扇区。鲁棒性分不丢。

### 3.2 缓存层：8 槽帧仓 + 压缩打包 + 原子提交（核心差异）

**存储格式改为压缩打包：4 像素 = 3 个 32 bit 字（24 bpp 无损，不降色深）。**

- 1 行 = 640 px × 3 B = 1920 B = **480 字**（整除，行边界永远字对齐，无跨行错位）
- 1 槽 = 480 字 × 480 行 = **230,400 字 = 921,600 B**
- 8 槽 = 1,843,200 字 = 7.37 MB；SDRAM 共 2,097,152 字，**余 253,952 字（约 0.97 MB）**

对比例程的"1 像素 1 字、低 8 位丢弃"：**同样 7.37 MB 例程只能放 6 张，我能放 8 张**，而且找不到任何"存了个恒零的字节"这种浪费。

**帧槽状态机**：

| 槽状态 | 含义 |
|---|---|
| `EMPTY` | 未装载 |
| `LOADING` | 正在从 SD 卡解码写入 |
| `READY` | 整幅写完，可显示 |
| `DISPLAYING` | 当前显示（可多槽，特效期间两个槽同时 `DISPLAYING`） |

- **上电时把卡里所有图全部预载进槽**（后台，用户无感），而不是"切一张读一张"
- 显示侧**只认 `READY`**；写侧完成整幅后**单拍原子置位**——显示永远看不到半帧。**撕裂是结构上不可能，不是"时机上大概率不会"**
- **读端口 2 个**（A/B），各自带独立行预取。这就是特效的硬件前提：混合两帧要求两帧同时可读——例程的乒乓结构做不到

**仲裁改为显示优先**（例程是读写互锁、无优先级）：

- 显示读端口：最高优先级，硬保证每行预取窗口内拿到 480 个字
- 装载写：空闲时突发写入，可被打断
- **读侧加 underrun 检测**：行预取没备齐就上报状态码，而不是静默重复像素

> 带宽核算：像素时钟 25 MHz。常态 1 字/像素 = 100 MB/s；过渡态读两帧 ≈ 200 MB/s。
> SDRAM 侧 125 MHz × 32 bit → 峰值 500 MB/s。余量 2.5×。
> SD 写入 ~1–3 MB/s，可忽略。**带宽不是瓶颈，瓶颈是仲裁公平性——正是例程缺的那一环。**

### 3.3 显示层：行预取 + 可编程混合器

```
frame_store.rd_a ──> 字节解包器 A ──> line_buf_a (ERAM32K ×1) ─┐
frame_store.rd_b ──> 字节解包器 B ──> line_buf_b (ERAM32K ×1) ─┴─> frame_mixer ──> osd ──> rgb_to_axis ──> HDMI core
video_timing (640×480@60) ─────────────────────────────────────────────┘
```

- **字节解包器**：行缓冲里存的是打包字。用一个 32 bit 桶形移位器，每像素消耗 3 字节，不足 3 字节就补读下一个字 → 平均 **0.75 字/像素**，25 MHz 下毫无压力。
- `frame_mixer` 三种模式，由配置寄存器选：
  - `MODE_DIRECT`：单帧直通
  - `MODE_FADE`：`out = (A×(255−α) + B×α) >> 8`，α 在可配时长内扫 0→255
  - `MODE_SLIDE`：按 `x` 与滑动位置比较选 A/B，带 1 像素软边
- `osd`：底部画一条**缩略图带**——1/8 步进采样直接对帧仓取值（`x/8, y/8`），**不额外占存储**；再叠一个当前图序号/轮播周期/特效/音量/状态码的数字条
- 这三件事都落在赛题扩展要求 (1) 上，且**例程一行都没有**

**行缓冲容量核算**：打包后 1 行 = 480 字 × 32 bit。`ERAM32K` 在 1024×32 配置下**一块就够一行**（深度 1024 ≥ 480）。两条行缓冲 = 2 块，占 16 块中的 2 块。

### 3.4 音频层：同时钟域直接 PCM 合成 + 每图音轨

**砍掉整条例程音频链**：不要 `PLL_HDMI_AUDIO`，不要 `hdmi_audio_tone_i2s_64fs`，不要 `I2S_receiver`。

```
video_clk(25 MHz) ──> audio_clk_gen  分数累加器 6/3125 → 精确 48.000 kHz 采样节拍
                            ↓
audio_track_table   每张图绑定一条曲目 {音符号序列, 速度, 波形, 包络}
                            ↓
wavetable_osc ×3    主旋律 + 和声 + 低音；24bit 相位累加器 + 正弦/三角查表
                            ↓
audio_mixer         混音 + 音量 + ADSR + 切图 20 ms 淡入淡出（防爆音）
                            ↓
acr_gen             N = 6144；CTS 由「像素时钟 / 采样率」**静态算出** = 25000
                            ↓
HDMI core 的 I_audio_left/right + I_audio_valid + I_acr_cts/n
```

逐条对应例程指纹：

| 例程指纹 | 我的做法 |
|---|---|
| 独立 12.288 MHz 音频 PLL | **不要 PLL**，直接复用像素时钟 |
| 方波 DDS（32bit 累加器只取 bit31） | **波表查表**正弦/三角，3 声部 |
| 自造"64bit 声道槽" I2S + 自己解回来 | **不产生 I2S**，直接给 core 并行 24bit PCM |
| 8 音符硬编码循环，与图片无关 | **每张图一条曲目**，切图切曲 + 交叉淡化 + 提示音 |
| CTS 实时测量（±40 ppm 量化误差） | **静态算出**：`CTS = N·f_pixel/(128·fs) = 6144×25e6/(128×48000) = 25000`，零误差 |
| 跨域靠 I2S 三线三拍同步器 | **不存在跨域**——音频全程在 `video_clk` 域 |

**48 kHz 是精确的**：25,000,000 / 48,000 = 3125/6，用模 3125 加 6 的累加器，长期平均误差为 0。抖动 ±40 ns，对音频重建无影响。

> ⚠️ 待验证的一点：加密 core 文档写明「音频输入数据的速率需要等于音频采样率，1 秒内需发送 48000 次音频数据」，且 `AUDIO_SAMPLE_RATE` 参数负责生成 channel status。
> 我的分数累加器给出的 `audio_valid` 平均正好 48000/s，符合该约定，但**相邻样本间隔会在 520/521 个 25 MHz 周期之间抖动**（±40 ns）。
> 例程的 I2S 自环方案间隔是均匀的。**这是需要仿真/上板验证的第一风险点**——若 core 对抖动敏感，退路是改成"乒乓双相位"输出或加一级 48 kHz 均匀化缓冲。

### 3.5 控制层：双键多态 + 片上 ADC + UART

- `key1`（B2）：短按 = 下一张；长按 ≥1 s = 循环切换特效（直通/淡入淡出/滑动）
- `key2`（C1）：短按 = 自动轮播开/关；**长按 = 循环切换轮播周期**（3/5/8/12/20 s）
  → 满足"另一个按键用于启动/停止自动轮播；**轮播周期可配置**"（例程是编译期常量）
- 8 位数码管改为显示 `图序号 | 周期 | 特效 | 音量 | 状态码`
- 片上 ADC / UART：**引脚待查**（见 §5）

> ⚠️ 引脚纪律：`pin.adc` 里只定义了 `key1=B2`、`key2=C1`。
> 板上还有 2 个按键、4 个拨码、UART、蜂鸣器，但**引脚号在工作区里没有权威来源**（原理图是 PDF）。
> **在拿到引脚之前不写任何新引脚，也不臆造。**

## 6. 验证策略（重要：**目前手上没有开发板**）
